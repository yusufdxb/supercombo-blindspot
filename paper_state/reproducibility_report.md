## Seeds

- Seeds set? YES for every stochastic step in the analysis path.
- Bootstrap CI (n=1000, seed=42): hardcoded at the module level in both
  `scripts/build_metrics.py:45-46` (SEED=42) and `src/ablations.py:25-26` (SEED=42),
  and passed to `src/metrics.py:bootstrap_ci(..., seed=42)` which constructs a

  `metrics_collected.npz` output under `meta__seed` for traceability.

  `src/baselines.py:149,167`. The GMM scores are loaded from the committed
  `report/baselines_collected.npz` cache when present, bypassing the stochastic step
  for normal reruns of `scripts/build_metrics.py`.
- PCA-Mahalanobis: deterministic (no random component; PCA fit is eigen-decomposition).
- E7 corruption analysis: `src/e7_corruption.py:575,610` hardcodes `seed=42` for its
  bootstrap calls.
- E1/E2/E3/E4/E4-RAM: fully deterministic (no sampling, no bootstrap).
- GAPS: none. Every stochastic step that appears in a published number carries a fixed
  seed.

## Draft vs. reality discrepancies

### Gap 1 (CRITICAL): Section 8 contains a `[TODO: verify]` that is unresolved.

Section 8 of `drafts/main_draft.md` (line 589) states:
> "[TODO: verify] the final cache-distribution decision (LFS versus regeneration script)
> before the public release, and confirm that a fresh clone plus `git lfs pull` recovers
> the E5 and E7 caches."

This TODO is not resolved. Git LFS is not configured in the repo (no `.gitattributes` LFS
entries, no `git lfs track` commands). A fresh clone therefore cannot recover E5 or E7
caches regardless of whether `git lfs pull` is run. Section 8 must be corrected before
submission: either the LFS tracking is implemented and tested, or Section 8 must state
explicitly which experiments cannot be re-run from a fresh clone.

### Gap 2 (MEDIUM): README "Reproduce" section claims cache-based re-run for E5, E7, and E4-RAM; all three claims are false on a fresh clone.

README lines 337-347 state:
- "Analysis runs from the committed cache without either dependency
  (`python -m src.e5_submodule`)."
- "Analysis runs from the cache (`python -m src.e7_corruption`)."
- "Analysis runs from the cache (`python -m src.e4_ram`)."

All three caches (e5_submodule_collected.npz, e7_collected.npz, e4_ram_collected.npz) are
gitignored. On a fresh clone, all three commands fail with FileNotFoundError or
BadZipFile. The word "committed" in the E5 submodule description is incorrect; the file

### Gap 3 (MEDIUM): e5_collected.npz is locally corrupt.

The 3.9 GB `report/e5_collected.npz` on the author's machine has a valid ZIP header but
no valid End-of-Central-Directory record. It cannot be opened by Python's zipfile or

to regenerate it, which requires GPU + CARLA + the commit data. This is a local issue
(the file is gitignored and not part of the public repo), but it means the author's
machine cannot re-run the E5 layer analysis from cache either.

### Gap 4 (MINOR): No path to obtain `data/` and `models/supercombo.onnx` is documented.

The README says parity reruns require these inputs but does not state the fetch command or
URL. The openpilot v0.9.7 tag and comma's segment hosting are implied but not linked. A
reviewer who clones the repo and wants to re-run parity has no documented starting point.
A single line in the README pointing to the v0.9.7 release asset and the comma segment

## Verdict

The paper's core claims (E1/E2/E3 collapse, E4 Subaru cliff, E6 AUROC/LOCO FPR,
ablations) are mechanically reproducible from a fresh public clone today, in under a
minute, with no GPU and no external data. This is the strongest reproducibility posture
for the paper's headline result. The committed figures are identical to what the analysis
scripts regenerate.

However, four experiments cannot be re-run from a fresh clone, and the draft and README
contain claims that these experiments CAN be re-run from caches:

1. E4-RAM (28 MB cache gitignored): the README says "analysis runs from the cache" -- this
   is false on a fresh clone.
2. E5 submodule (98 MB cache gitignored): the README says "analysis runs from the committed
   cache" -- the word "committed" is wrong; the file is gitignored.
3. E7 corruption sweep (110 MB cache gitignored): the README says "analysis runs from the
   cache" -- false on a fresh clone.
4. E5 layer (3.9 GB cache gitignored AND corrupt locally): no fresh-clone recovery path
   exists.
5. Parity re-run requires gitignored data and model files with no documented fetch path.

Section 8 of the draft paper carries an unresolved `[TODO: verify]` on exactly this issue.

**Classification: reproducible with documented gaps.**

The gaps that must become explicit limitations in the paper:

- L1: Section 8 must remove the `[TODO: verify]` and state precisely which experiments
  (E4-RAM, E5, E7) cannot be re-run from a fresh public clone, and what a reviewer
  must do to re-run them (e.g., Git LFS pull, regeneration script, or "these caches
  are available on request").
- L2: The README "Reproduce" section must not claim that E5, E7, or E4-RAM "run from the
  cache" without stating that the caches are not in the public repo. Each of those three
  paragraphs should add: "(cache not included in the public repo; requires --collect pass
  with GPU + data)".
- L3: The E5 cache should be refactored: the 3.9 GB full-tensor file should be replaced
  by a committed ~100 KB summary array (activity ratios per stage per alpha), which is
  all the analysis ever reads.
- L4 (minor): A single documented fetch command for `models/supercombo.onnx` and the
  comma segment should be added to the README parity section.

None of these gaps touch the correctness of the reported numbers. The headline results
reproduce; the gaps are in the re-run path for the supporting localization and
corruption experiments.

What was not verified:
- That a `git lfs pull` would successfully restore the missing caches (LFS is not configured).
- That the collect passes (`--collect` flags) produce numerically identical outputs on
  a different machine (they require matching GPU + CARLA environment and no seed is set
  for the CARLA rendering or frame capture steps).

Riskiest unverified assumption: the CARLA rendering and frame capture pipeline (used in all
`--collect` passes) is not seeded. If a reviewer re-collected E4 from scratch using a
different CARLA version or different NVIDIA driver, the rendered frames would differ from
the committed `e4_collected.npz` and the analysis numbers would differ from those in the
paper. This affects reproducibility of the collection step for all experiments; the
analysis-from-cache step is fully pinned and deterministic.
