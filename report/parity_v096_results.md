# Parity: reimplemented v0.9.6 supercombo vs comma v0.9.6 reference  `[verified 2026-05-30]`

Second-model foundation gate. Our reimplemented openpilot **v0.9.6** `supercombo` inference
(same harness as v0.9.7, plus the two zeroed nav inputs at the stock no-navigation operating
point) matches comma's own v0.9.6 `model_replay` reference output. This establishes the v0.9.6
path is correct before any teardown is run on it. Regenerated by
`python -m src.run_parity --model v096`.

Acceptance criterion (`src/run_parity.py`): `|delta| <= 0.5 m/s^2` for `>= 95%` of frames
after a 40-frame (2 s at 20 Hz) warm-up trim. The compared quantity is the longitudinal
acceleration head `accel_t0`; reference = comma's logged v0.9.6 modelV2 trace (model_replay),
ours = the parsed `accel_t0` from the reimplemented v0.9.6 path with correct recurrent-state
threading, unnormalized YUV input, and `nav_features`/`nav_instructions` fed as zeroed float16.

## Source / reference / mapping

- Source: **CI TEST_ROUTE seg-6** `data/ci_v096_source/{fcamera.hevc, rlog.bz2}`
  (dongle `2f4452b03ccb98f0`, route `2022-12-03--13-45-30`, seg 6; comma 3 narrow road cam).
  The v0.9.6 reference is matched to THIS route, **not** to the Subaru v0.9.7 route.
- Reference: comma's v0.9.6 model_replay trace `data/ci_v096_ref/model_ref.bz2`
  (600 modelV2 frames, frameId 1..600, all with `acceleration.x` length >= 33).
- liveCalibration (seg-6 source rlog): `rpyCalib = [+0.00106, +0.08525, -0.01673] rad`.
- **frameId mapping (structural, NOT tuned):** comma's `model_replay` re-bases `modelV2.frameId`
  to a 1-based sequential index over the camera frames it processes. Verified on the Subaru
  v0.9.7 route (source roadCameraState frameIds 3603..4802, regen modelV2 1..1199 -> hevc index
  K maps to reference frameId K). Applying the identical positional rule here: seg-6 source
  roadCameraState frameIds 7205..8404, reference frameIds 1..600 -> **reference frameId R == hevc
  index R, offset = 0**. Read off the frameId ranges in `derive_frame_offset()`; the offset is
  not adjusted to maximise parity.

## v0.9.6 contract vs v0.9.7 (verified)

- Inputs: the 7 v0.9.7 inputs **plus** `nav_features` (1,256) fp16 and `nav_instructions`
  (1,150) fp16. Both zeroed at the no-navigation operating point (comma-faithful: openpilot
  v0.9.6 `modeld.py:247-249` zeros them when nav is disabled, the default).
- `features_buffer` stays (1,99,512); `desire` stays (1,100,8); `prev_desired_curv` stays (1,100,1).
- Output stays (1,6504); `output_slices` is byte-identical to v0.9.7 (15 slices summing to 6504,
  `hidden_state == slice(5992, None)`).
- The harness feeds the nav inputs ONLY when the loaded session exposes them, so the v0.9.7
  path runs unchanged.

## Reproduce

- Fetch inputs (reproducibility artifact, `data/` + `models/*.onnx` are gitignored):
  `env -u PYTHONPATH .venv/bin/python -m scripts.fetch_upgrade_data`
- Run parity:
  `env -u PYTHONPATH .venv/bin/python -m src.run_parity --model v096`
- Tests:
  `env -u PYTHONPATH .venv/bin/python -m pytest tests/test_second_model.py -v`
- Dependencies: `onnxruntime-gpu==1.23.2`, `pycapnp` (rlog decode), ffmpeg (hevc decode).
  All pinned in `requirements.txt`. No CARLA. GPU optional (CPU EP also works, slower).
